# METATYA Engineering Standard
## استاندارد مادر مهندسی و معماری METATYA Sports OS

- **وضعیت:** استاندارد مرجع پروژه
- **دامنه:** تمام قابلیت‌های مشترک Sports OS و تمام رشته‌های ورزشی فعلی و آینده
- **اصل حاکم:** هر قانون مصوب باید در همین سند ثبت شود، در طراحی و کد اعمال شود و با شواهد قابل بررسی کنترل شود.
- **زبان مرجع:** فارسی؛ نام فنی اجزا و قراردادها به انگلیسی حفظ می‌شود.

این سند مرجع واحد قواعد مهندسی این مخزن است. گفت‌وگو، پیام، توضیح شفاهی یا کامنت کد جایگزین این سند نیست. اگر تصمیم معماری جدیدی گرفته شد، پیش از اجرای آن باید همین سند به‌روزرسانی شود یا تصمیم به‌صورت موقت و دارای تاریخ انقضا در بخش تصمیم‌های باز ثبت شود.

---

## 1. معماری محصول: Shared Core + Sport Modules

### 1.1 هسته مشترک
قابلیت‌هایی که بین رشته‌ها مشترک‌اند فقط یک‌بار در هسته ساخته و نگهداری می‌شوند؛ از جمله:
- سازمان‌ها، هیئت‌ها، باشگاه‌ها و چندمستاجری (Tenancy)
- کاربران، عضویت‌ها، نقش‌ها و مجوزها
- پرونده پایه ورزشکار/عضو و ارتباط با مربی، داور و مدیر
- رویدادها، مسابقات، ثبت‌نام، نتایج و سوابق
- احراز هویت، کنترل دسترسی، ممیزی و ثبت رویداد
- اعلان‌ها، گزارش‌ها، فایل‌ها، پرداخت‌ها و اشتراک‌ها در صورت تصویب دامنه
- تنظیمات، پیکربندی، پشتیبان‌گیری و بازیابی
- APIها، اعتبارسنجی، خطاها، مشاهده‌پذیری و تست‌های مشترک

### 1.2 ماژول اختصاصی هر رشته
هر رشته فقط منطق، فرم‌ها، داده‌ها، قوانین و گردش‌کار اختصاصی خودش را در ماژول مستقل نگه می‌دارد. ماژول رشته نباید نسخه کپی‌شده‌ای از احراز هویت، tenant، اعضا، نقش‌ها، اعلان‌ها یا سایر قابلیت‌های هسته بسازد.

### 1.3 قانون توسعه رشته جدید
پیش از شروع هر رشته جدید:
1. نیازمندی را با قابلیت‌های موجود هسته تطبیق بده.
2. قابلیت مشترک موجود را دوباره پیاده‌سازی نکن.
3. فقط شکاف واقعی را به هسته یا ماژول اختصاصی اضافه کن.
4. قرارداد API و مدل داده را مستند کن.
5. تست‌های مشترک و تست‌های اختصاصی رشته را اجرا کن.
6. مستند راه‌اندازی رشته را به‌روزرسانی کن.

## 2. قواعد چندمستاجری و مالکیت داده

- تمام داده‌های سازمانی باید به tenant معتبر و مجاز متصل باشند.
- tenant فعال باید در سمت سرور از نشست معتبر و عضویت فعال کاربر تعیین شود؛ شناسه ارسالی مرورگر به‌تنهایی منبع اعتماد نیست.
- هیچ tenant ID آزمایشی یا ثابت نباید در کد عملیاتی hard-code شود.
- اگر کاربر چند عضویت فعال دارد، انتخاب tenant باید صریح و قابل اعتبارسنجی باشد؛ انتخاب تصادفی یا حدس‌زدن ممنوع است.
- تمام خواندن‌ها و نوشتن‌ها باید در محدوده tenant انجام شوند.
- RLS در دیتابیس لایه دفاعی ضروری است و جایگزین کنترل مجوز در API نیست؛ هر دو باید اعمال شوند.
- تست جداسازی باید ثابت کند کاربر tenant A نمی‌تواند داده tenant B را بخواند، تغییر دهد یا حذف کند.
- دسترسی بین tenantها فقط از مسیر مجوز مشخص، محدود، ثبت‌شده و قابل ممیزی مجاز است.

---

## 3. قرارداد دیتابیس و API

- schema، نام جدول‌ها، ستون‌ها، نوع داده‌ها، روابط و RPCها باید از migrationهای واقعی و وضعیت دیتابیس هدف استخراج شوند؛ از روی نام‌گذاری یا حدس کدنویسی نکن.
- هر تغییر schema باید migration نسخه‌بندی‌شده، قابل بازبینی و دارای مسیر rollback یا برنامه بازیابی داشته باشد.
- migration اجراشده را بدون بررسی تاریخچه و داده‌های موجود دوباره اجرا نکن.
- کد برنامه، TypeScript types، سرویس‌ها و API routes باید با schema واقعی یکسان باشند.
- قرارداد API باید ورودی، خروجی، نقش‌های مجاز، خطاها و الزامات tenant را روشن کند.
- خطای دیتابیس نباید با پیام موفقیت یا فهرست خالی پنهان شود؛ خطا باید امن، قابل فهم و قابل ردیابی گزارش شود.
- عملیات حساس باید سمت سرور انجام شود. کلیدهای محرمانه هرگز در مرورگر یا متغیرهای `NEXT_PUBLIC_*` قرار نگیرند.

## 4. امنیت، حریم خصوصی و حاکمیت دسترسی

- امنیت و حریم خصوصی از روز اول الزامی‌اند، نه مرحله پایانی.
- اصل حداقل دسترسی (Least Privilege) برای کاربران، سرویس‌ها، توکن‌ها و پیمانکاران اعمال شود.
- هیچ شخص یا سرویس ثالثی بدون مجوز صریح، معتبر، محدود به دامنه و قابل اثبات مالک، حق دسترسی یا استفاده از دارایی‌های پروژه را ندارد.
- اسرار، کلیدها، توکن‌ها و داده‌های شخصی در Git، log، پیام خطا یا خروجی عمومی افشا نشوند.
- داده‌های کودکان و نوجوانان، اطلاعات تماس، پزشکی، مالی و بیمه‌ای حساس تلقی شوند؛ جمع‌آوری آن‌ها باید ضروری، محدود، مجاز و دارای کنترل دسترسی و رضایت‌های قانونی لازم باشد.
- رویدادهای مهم امنیتی و تغییرات مدیریتی باید audit trail داشته باشند؛ log نباید حاوی secret یا داده حساس غیرضروری باشد.
- آپلود فایل باید از نظر نوع، اندازه، مجوز دسترسی و محتوای ناامن اعتبارسنجی شود.
- دفاع در برابر ورودی مخرب، اسپم، سوءاستفاده از API و دسترسی غیرمجاز باید در لایه‌های مناسب پیاده‌سازی و آزمایش شود.

---

## 5. صحت داده و کیفیت خروجی

- داده تأییدنشده نباید به‌عنوان داده قطعی نمایش داده شود.
- منشأ، زمان ثبت، ثبت‌کننده و وضعیت تأیید داده‌های مهم باید مشخص باشد.
- ورودی‌ها در سمت سرور اعتبارسنجی شوند؛ اعتبارسنجی رابط کاربری به‌تنهایی کافی نیست.
- قواعد محاسباتی و رتبه‌بندی باید مستند و دارای تست مرزی باشند.
- اصلاح یا حذف داده‌های مهم باید مجاز، قابل ممیزی و در صورت نیاز قابل بازیابی باشد.
- داده آزمایشی باید آشکارا برچسب‌گذاری شود و با داده واقعی اشتباه نشود.

---

## 6. پایداری، پشتیبان‌گیری و بازیابی

- برای داده‌های مهم، برنامه پشتیبان‌گیری رمزگذاری‌شده و محدود به دسترسی مجاز تعریف شود.
- بازیابی باید بدون حذف یا تغییر ناخواسته داده‌های دیگر قابل آزمایش باشد.
- نسخه پشتیبان به‌تنهایی کافی نیست؛ آزمون بازیابی دوره‌ای لازم است.
- تغییرات پرخطر ابتدا در محیط توسعه یا staging آزمایش شوند.
- عملیات تکرارشونده حساس باید تا حد امکان idempotent طراحی شوند.
- خطاها، سلامت سرویس، زمان پاسخ و ظرفیت منابع باید قابل مشاهده و پایش باشند.

## 7. تست و دروازه‌های کیفیت

هیچ قابلیت مشترک یا ماژول رشته‌ای صرفاً به دلیل بازشدن صفحه «تکمیل‌شده» محسوب نمی‌شود.

### کنترل‌های پایه
- typecheck
- lint
- build
- تست واحد برای منطق دامنه
- تست API برای نقش‌ها و ورودی‌های معتبر/نامعتبر
- تست RLS و جداسازی tenant
- تست مسیرهای اصلی کاربر
- تست مهاجرت و سازگاری دیتابیس
- بررسی اسرار و متغیرهای محیطی

### تست‌های اجباری هسته
- کاربر بدون نشست نمی‌تواند به API محافظت‌شده دسترسی پیدا کند.
- کاربر بدون عضویت فعال نمی‌تواند داده tenant را ببیند یا تغییر دهد.
- نقش فاقد مجوز نمی‌تواند عملیات مدیریتی انجام دهد.
- کاربر یک tenant به داده tenant دیگر دسترسی ندارد.
- خطای پایگاه داده به‌صورت امن گزارش می‌شود و موفقیت کاذب تولید نمی‌کند.

### تعریف وضعیت
- **طراحی‌شده:** مستند شده، اما پیاده‌سازی یا تست نشده است.
- **پیاده‌سازی‌شده:** کد نوشته شده، اما همه آزمون‌های لازم موفق نشده‌اند.
- **تأییدشده:** آزمون‌های مربوطه اجرا شده و شواهد نتیجه ثبت شده‌اند.
- **آماده انتشار:** کنترل‌های امنیتی، داده، استقرار، پشتیبان‌گیری و آزمون پذیرش نیز تأیید شده‌اند.

در گزارش وضعیت از درصد یا ادعای موفقیت بدون شواهد استفاده نکن.

## 8. استاندارد تغییر کد و مخزن

- پیش از تغییر، فایل‌ها و وابستگی‌های مرتبط را بررسی کن؛ از اصلاح حدسی و ناقص خودداری کن.
- تغییر باید حداقل دامنه لازم را داشته باشد و از بازنویسی بی‌دلیل بخش‌های سالم پرهیز شود.
- نام‌گذاری، ساختار پوشه‌ها و قراردادهای مشترک باید ثابت و مستند بمانند.
- تغییرات مرتبط با هم باید به‌صورت یک مجموعه قابل بازبینی ارائه شوند.
- فایل کامل جایگزین‌شونده باید با مسیر دقیق و دستور اجرای روشن معرفی شود.
- قبل از commit، diff و وضعیت مخزن بررسی شوند.
- هیچ‌گاه فایل محیطی، secret یا داده شخصی واقعی commit نشود.
- تغییرات دیتابیس، امنیت، دسترسی و داده واقعی باید پیش از اجرا ارزیابی ریسک شوند.
- نتیجه هر مرحله با commit، خروجی تست یا شواهد قابل تکرار ثبت شود.

## 11. تصمیم‌های معماری ثبت‌شده

### ADR-001 — هسته مشترک و ماژول‌های رشته‌ای
- **تصمیم:** Sports OS بر پایه Shared Core + Sport-Specific Modules ساخته می‌شود.
- **پیامد:** قابلیت مشترک فقط یک‌بار توسعه می‌یابد؛ رشته‌ها منطق اختصاصی خود را به‌صورت ماژول ارائه می‌کنند.
- **وضعیت:** اصل معماری مصوب؛ انطباق کامل کد نیازمند ممیزی و تست است.

### ADR-002 — منبع حقیقت tenant
- **تصمیم:** tenant فعال از نشست احراز هویت‌شده و عضویت معتبر سمت سرور تعیین می‌شود؛ ورودی کلاینت به‌تنهایی قابل اعتماد نیست.
- **وضعیت:** الزام مصوب؛ پیاده‌سازی فعلی باید ممیزی و اصلاح شود.

### ADR-003 — انطباق schema برنامه و دیتابیس
- **تصمیم:** migrationها و schema واقعی دیتابیس منبع حقیقت ساختار داده‌اند؛ کد باید با آن‌ها منطبق باشد.
- **وضعیت:** در ممیزی اخیر، اختلاف `sports_core` و `public` مشاهده شده و رفع آن باز است.

## 12. کارهای باز برای انطباق نسخه فعلی

این موارد تا زمان پیاده‌سازی و تست، باز محسوب می‌شوند:
- [ ] یکسان‌سازی schema مورد استفاده برنامه با schema واقعی Supabase
- [ ] پیاده‌سازی tenant resolution امن سمت سرور
- [ ] تطبیق نقش‌های واقعی membership با نقش‌های هسته
- [ ] تطبیق مدل‌ها و سرویس‌ها با ستون‌های واقعی جداول
- [ ] افزودن تست‌های RLS و جداسازی tenant
- [ ] تست کامل ایجاد، فهرست‌کردن و مدیریت عضو، رویداد و نتیجه
- [ ] اجرای typecheck، lint و build و ثبت خروجی
- [ ] به‌روزرسانی وضعیت و شواهد در مستند پیاده‌سازی

**قاعده نهایی:** هیچ قانون مصوبی نباید فقط در حافظه افراد یا مکالمه باقی بماند؛ باید در این سند یا سند فنی پیوندخورده ثبت، در کد اعمال و با تست قابل اثبات شود.
