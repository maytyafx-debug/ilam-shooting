**Scope:** Next.js application under `sports-os/` and the proposed Supabase schema in `supabase/migrations/`.  
**Status:** security hardening in progress; **not approved for production or real athlete/minor data**.

## 1. Authentication and sessions

- **IMPLEMENTED:** Supabase Auth password login uses `signInWithPassword` through the Supabase SSR browser client.
- **IMPLEMENTED:** the server client reads/writes the Supabase SSR cookie session.
- **IMPLEMENTED:** middleware calls `auth.getUser()` to refresh/validate the session and redirects unauthenticated requests for the dashboard to `/login`.
- **IMPLEMENTED:** the Auth callback exchanges the one-time authorization code and accepts only a safe relative `next` path; callback failures return to the login page.
- **IMPLEMENTED:** logout is performed by a server route using `auth.signOut()`, which clears the server-managed session cookies.
- **STATIC-TESTED:** source-level checks cover the login, callback, middleware, logout route and role guard.
- **NOT LIVE-VERIFIED:** password login, callback exchange, cookie rotation, expiry, refresh and logout must be tested against the target Supabase Auth project.
- **Operational requirement:** configure the exact production Site URL and redirect allow-list in Supabase Auth. Do not use wildcard production redirects.

## 2. RBAC

The current schema defines these persisted roles:

| Stored role | Intended product role | Allowed operations |
|---|---|---|
| `admin` | هیئت / سازمان مدیر | manage members and events; read data; administer profiles |
| `referee` | داور | read operational members/events; record results |
| `member` | ورزشکار | read only their linked member record and own results through RLS |

- **IMPLEMENTED:** API handlers call `requireCoreRole`; unauthenticated requests receive 401 and missing/invalid/disallowed profiles receive 403.
- **IMPLEMENTED:** the role guard obtains the user through `auth.getUser()`; it does not trust a role supplied by the browser or user metadata.
- **IMPLEMENTED:** role values are allow-listed before authorization succeeds.
- **IMPORTANT LIMITATION:** no public self-registration or client-side role assignment is provided. An administrator must be provisioned through a trusted owner-controlled process.
- **NOT LIVE-VERIFIED:** create test users for all three roles and verify positive and negative cases against the deployed database.

## 3. Row Level Security

Migration `supabase/migrations/005_sports_os_namespaced.sql` defines RLS on the six `sports_core` operational tables.

Expected policy behavior:
- Athlete/member profile: read only the profile row whose ID equals `auth.uid()`.
- Athlete/member record: read only the member row linked through `profile_id = auth.uid()`.
- Athlete/member result: read only results whose member row is linked to `auth.uid()`.
- Referee: read operational members/events and insert results only when `recorded_by = auth.uid()`.
- Admin: manage operational records and profiles.
- Audit log: readable only by admin; writes are generated by database triggers.

**BLOCKER / NOT LIVE-VERIFIED:** the migration is repository source, not proof that it has been applied to the target Supabase project. Verify migration history, effective grants, policies, function ownership and RLS behavior in the target project before using real data. Do not apply migrations automatically as part of deployment.

## 4. Multi-tenancy and organization isolation

**BLOCKER — multi-tenancy is not yet implemented in the operational `sports_core` schema.**

The current operational model has `sports_clubs` and nullable `club_id` fields, but it has no authoritative tenant-membership relation and no `tenant_id` on operational rows. The current admin/referee policies are role-wide rather than tenant-scoped. Therefore, the current model is suitable only for a single isolated pilot environment; it does **not** prove isolation between multiple clubs or federations.

Before enabling multiple organizations, implement and test:
1. A tenant/organization registry and membership table with explicit tenant-scoped roles.
2. Non-null tenant ownership on every tenant-owned operational row (including members, events, results, files and audit records).
3. Composite foreign keys or equivalent database constraints preventing cross-tenant references.
4. RLS predicates that verify both the authenticated user and active membership in the row's tenant.
5. Server-side tenant resolution and authorization. A tenant ID supplied by a browser is a selector only, never proof of access.
6. Negative integration tests proving tenant A cannot read, insert, update, delete, reference or infer tenant B records.
7. A reviewed backfill/bootstrap plan for existing rows before enforcing non-null tenant ownership.

Do not onboard a second club/federation or store its records until this blocker is closed. The separate public `sports_tenants` proposal in `sports-os/database/001_core.sql` is not wired to the current `sports_core` operational tables and must not be treated as an implemented substitute.

## 5. Secrets, environment and data handling

- Only the Supabase project URL and publishable/anon key belong in `NEXT_PUBLIC_*` variables.
- Never expose a service-role key, database password, JWT secret or other privileged credential to browser code or commit it to Git.
- Keep environment files with real secrets out of Git; use the ignored local env file and the hosting provider's secret store.
- Do not import real athlete, guardian, insurance, finance or minor data until tenant isolation, consent, least-privilege access, retention and recovery controls are implemented and verified.
